# C3: an `actions/cache` key for each of 12 package managers, run

**Question.** For each of 12 package managers, does a `key`, `restore-keys` and `path` recipe for `actions/cache` (v6) save on a first run and restore on a second, on a fresh runner each time? And what does the restore step's `cache-hit` output say in each case?

**Where.** This public repository, GitHub-hosted `ubuntu-24.04`, standard runner for public repositories (4 vCPU, 16 GB RAM, 14 GB SSD). The image version of every job is in its row (`image`).

**Fixtures.** `fixtures/<ecosystem>/` is one small real project per ecosystem with a real lockfile, made once by `.github/workflows/C3-fixtures.yml` running `make-fixtures.sh` and committed, so every run hashes the same bytes. Tool versions at that time are in `fixtures/TOOLS.txt`.

**Workflow.** `.github/workflows/C3-recipes.yml` is generated by `generate.py` (`C3-recipes-fixed.yml` by `generate.py --fixed`). Per ecosystem it has three jobs, each on its own runner:

1. `<eco>-cold`: `actions/cache/restore` must miss; install; `actions/cache/save`. The save uses the restore step's `cache-primary-key` output as its key.
2. `<eco>-warm`: needs cold. `actions/cache/restore` with the same key must be an exact hit (`cache-hit` is `true`); install.
3. `<eco>-edit`: needs warm. One byte is appended to the file the key is hashed from. The exact key must now miss, and the `restore-keys` prefix must restore the cold run's entry (`cache-hit` is `false`, `cache-matched-key` is set).

Each job fails if its expectation is not met, so a green job is a recipe that worked. The only addition to the recipe a reader would write is the prefix `c3-<run id>-` on every key, so that the cold run is a true miss however often the workflow is run. A last job deletes the run's entries.

**Key drift.** Every job also hashes the key's input files before and after the install with `hashFiles`, and records whether the two differ (`key_drift_during_install`), together with a `sha256sum` listing of the matching files before and after (`keydrift.txt` in the job's artifact when they differ). `C3-recipes.yml` uses the plain `**/<lockfile>` patterns; `C3-recipes-fixed.yml` adds exclusion patterns for the four ecosystems that drifted.

**Timings.** `restore_s`, `install_s` and `save_s` are wall-clock seconds around the step, measured with `date` in the neighbouring steps, so they include about a second of step start-up. They come from single runs and are not summarised: C3 is a pass/fail study. The repeated timings are in C2.

**Clearing caches.** `.github/workflows/C3-clear.yml` makes five tiny entries and deletes them with `gh cache delete` by key, `gh cache delete` by ID, the REST API by key, the REST API by ID and a list-and-delete loop, asserting the count of `gh cache list --key` after each.

**Results.** `results/recipes-<run id>.csv`, one row per job, with the date and run ID of each row.
